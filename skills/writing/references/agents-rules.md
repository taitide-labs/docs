# AI 规则编写规范

现代大模型已经非常强大，删除通用建议，只保留会影响模型判断与执行的规则或目标引导。

编写的目标是让文档行为可预测，即明确预期 Agent 阅读后会遵循何种行为。

## 通用规则

- 将具体问题抽象为通用原则，用稳定的行为约束覆盖整类场景，以适应工具演进与环境变化。仅当通用表述约束力不足时保留特定规则，例如用特定编程语言的惯用表达替代泛化白话，Agent 更能精准识别语义并迁移至其他语言。

### 触发词

大模型在预训练阶段已经充分掌握公认的工业标准与方法论，只需使用标准触发词调用先验知识，就能以最少的 Token 锚定整个行为区域，远比白话逐条解释精准。

- 当规则对应公认无歧义的标准或方法论时，直接使用触发词，例如 TDD、BCP 14、第一性原理等，按需补充需要收紧或调整的局部细节。
- 当触发词所表达的核心内容需要大幅裁剪才适用时，避免使用触发词，直接表述规则。

### 句式与情态词

规则使用纯文本与列表符，每条独立规则单独成行，省去面向人类扫读的加粗、斜体与装饰性表格，防止长段落分散注意力；除触发词与专业术语外，用词保持平实，语言自然连贯；规则不冲突、不重复。

- 当编写带触发前提的规则时，必须将条件放在句首，写成 `当 <触发条件> 时，<动作指令>`，因为模型采用自回归生成，条件前置能让动作词在预填充阶段即受因果掩码约束，防止未满足条件就先执行动作。
- 当编写倾向性引导规则时，写成 `<动作指令>，因为 <工程原因>` 或 `<动作指令>，以 <预期收益>`，帮助模型在未列举的边缘场景中按意图自主判断。

情态词遵循 BCP 14 规范，在中文规则中统一映射为“必须”“严禁”“应当”“优先”“避免”五个强度梯度。

- 并非每条规则都需要情态词，仅当规则需要被这个强度约束时使用。
- 默认使用正向词引导而非负向约束，滥用负向词会引发白熊效应。
- 当涉及权衡、存在合理例外时，使用“优先”与“应当”；当需要规避坏习惯时，追加 `而非 <坏习惯>`；当倾向的策略值得解释时，追加 `以避免 <负面影响>` 或 `以 <预期收益>`。
- “必须”与“严禁”只在拦截不可逆安全风险、或矫正极易触发的常见坏习惯时使用（如滥用 `grep` 与 `cat`）；每条“严禁”紧跟唯一合法的正向出口，写成 `严禁 <旧习惯>，应当使用 <新方案>`，存在唯一例外时补充 `仅当 <条件> 时使用 <备选路径>`。
- 当需要 Agent 按某种格式输出文档或内容时，优先使用占位格式，直接在代码块里说明写法，如：

    ```markdown
    # 固定文字不用占位
    <占位文字在<>内编写>
    ```

### 裁剪

- 遵循 SSOT 原则，删除重复内容与上下文、环境中可直接获取的信息（如目录结构、工具 Schema、工具 Help），仅在查找成本很高时保留。
- 逐句、逐词执行 No-op 检验，删除既不改变行为也无目标引导价值的废话，例如模型默认遵循或不会触发的空泛规则。
- 检查内容相关性，删除无关内容；若是按需加载的内容，优先拆分为独立文档并引用。

## 专属规则

- `SYSTEM.md`（即 System Prompt）仅限包含 Agent 身份、沟通风格、工具编排原则等通用规则。
- `AGENTS.md` 分为全局规则与仓库规则。全局规则同 `SYSTEM.md`；仓库规则只保留非默认的构建与测试命令、静态分析无法捕获的隐含业务约束，以及指向深层文档的路径映射，优先指向 `CONTRIBUTING.md`。
- 编写 `SKILL.md` 及其附属文件时，遵循 [skill-rules.md](skill-rules.md)。
