按约束确定性与反馈速度优先级加固工程防线：优先用安全抽象、类型系统与静态分析在编译前消除错误空间，其次用运行时属性与变异测试守住行为，仅当静态分析与自动化测试均无法机械判别语义意图时才补充极简自然语言规则。

## 选型优先级

1. 安全抽象与受限类型：当缺陷源于易误用的底层原语（如业务代码直接调用复杂副作用钩子、原始定时器或原生 SQL），优先封装高安全内部 API 并在业务层禁用直接调用；当缺陷源于非法值状态、精度丢失或状态机非法流转时，遵循 `Making Illegal States Unrepresentable`，在 `primitives` 或共享 `domain` 层封锁私有字段构造与状态签名，使错误写法在编译期报错。
2. 编译器与 Linter 约束：当问题表现为禁用阻塞调用、未包装浮点运算、隐式吞错或模块组织违规（如 `mod.rs`）时，优先配置编译器开关与静态检查规则（如 Rust 的 `Cargo.toml` `[workspace.lints]` 与 `clippy.toml` 禁用清单），而非在 `AGENTS.md` 追加文字提醒。
3. AST 结构与禁注释规则：当规则涉及同包内跨切片互引、读路径违规引用写侧领域模型、纯计算模块引入异步运行库、叶子源码内联测试或业务代码残留普通行内注释时，在 `rules/*.yml` 编写 `ast-grep` 或 Linter 规则拦截（注释类规则仅豁免编译器或工具链消费的 `///`、`// SAFETY:` 与带 `reason` 的编译豁免），并与类型敏感的 Linter 互补配合。
4. 自然语言兜底：当问题完全依赖纯语义判断（如跨模块命名品味或人工协作约定）且前三层均无法机械判别时，才按照条件前置与单一事实源准则提炼为一条极简 `AGENTS.md` 规则。

## 执行流程

1. 根因归类：定位触发误用的深层机制，避免仅针对单次表面语法编写脆弱补丁；清理存量代码注释时，将赘述与过时注释直接删除，将借口注释删除并修复根因（或建单追踪），将局部反直觉绕过固化为命名精准的回归测试，将非显而易见的架构决策移入 ADR。
2. 编写自包含修复指引的报错文案：严禁编写含糊的否定警告或复读编译器前缀主语，必须在每条新增规则的 `reason` 或 `message` 字段直接写明具体工程危害与唯一正向替代方案，并在最小正反测试样本上实测触发行为。
3. 存量扫描与通过 PR 合入：规则入库后立即执行 `mise run check` 扫描存量代码；小规模历史违规在同一分支内一次性迁移清零，大规模存量违规采用 Ratchet 策略禁止新增并逐批收紧；严禁直接推送 `main`，必须确认全量门禁通过后推送独立分支创建 PR 合入 `main`。
