以独立审计视角验证待合入变更或发版基线，核查自动化测试的有效覆盖与防投机，并输出便于快速审阅的交付审查摘要。严禁直接修改被测业务代码以掩盖缺陷，必须输出精确复现证据打回原切片分支修复；当暴露出共性架构违规或重复缺陷时，使用 `guardrail` Skill 固化为静态防线。

## 验证流程

1. 确定性门禁与防投机核查：
   - 执行 `mise run check` 确认全量静态检查与自动化测试通过。
   - 核查 `git diff`，确认实现分支未篡改既有黑盒验收测试断言（仅允许移除工单显式授权取代的旧规则场景）；审计单切片 PR 时确认本工单目标场景及新增测试无残留 `wip` 跳过标记，审计端到端联调或发版基线时确认全仓无未授权 `wip` 残留。
   - 审查新增单元测试是否存在无有效断言的 `Reward Hacking` 投机测试；当改动涉及核心领域规则或边界状态机时，运行 `Mutation Testing` 工具（如 `cargo-mutants`）校验测试集能否有效捕获逻辑变异。
   - 核查变更代码是否存在违规普通代码注释（赘述、借口或过时注释，仅豁免编译器与工具链消费的结构化注释）。
2. 契约与统一语言对齐：
   - 对照所属 `context.md`、`context-map.md` 与已合入 ADR，核查新增类型、字段、路由、命令与界面文案是否严格对齐统一语言 `等价` 标识符且未混入 `避免` 禁用词。
   - 当对外接口契约发生变更时，严禁全文阅读原始 `contracts/openapi.json`，必须通过兼容性工具（如 `oasdiff`）的输出校验其遵循 `Parallel Change` 向后兼容规则。
   - 检查读路径查询实现是否存在 N+1 查询退化。
3. 并发不变量与交互表面复核：
   - 当写路径涉及状态锁定、并发竞争或跨边界资源预占与释放时，校验是否具备覆盖随机时序不变量的 `Property-Based Testing`（如 `proptest-state-machine`）。
   - 当变更涉及图形客户端时，对照 `DESIGN.md` 核查静态守卫测试（无硬编码色值、亮暗主题键值对称）与无头交互验收测试；仅当界面布局或交互发生实质变更时，在真实宿主通过无障碍树与视觉截图复核亮暗双主题与多端视口，发版巡检或大幅交互变更时辅以探索性随机交互测试排查竞态与崩溃。
   - 当变更涉及命令行应用时，在真实终端复核 `--help`、结构化输出、`stdout` 与 `stderr` 流隔离及退出码语义。
4. 输出交付审查摘要：必须如实列出全部验证结果（含失败与跳过项），汇总验证范围、状态机与契约影响面、并发与表面复核证据以及建议沉淀为静态防线的条目；当变更涉及状态流转或用户界面时，附带 Mermaid 状态图与验证截图或录屏路径。
