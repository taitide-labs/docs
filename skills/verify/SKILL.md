站在独立破坏者与审慎审计员视角验证待合入变更或发版基线，压实自动化测试真实杀伤力并收敛出供人类在数秒内完成审阅的沙漏下口凭证。严禁既当裁判又当运动员直接下场修改被测业务代码以掩盖缺陷；当抓出实现错误时必须输出精确复现证据打回原切片分支修复，当暴露出共性结构或坏味道缺陷时读取并转交 [guardrail](../guardrail/SKILL.md) 固化为静态防线。

## 验证流程

1. 确定性门禁与防投机核查：执行 `mise run check` 确认全量静态与单元测试基线通过；核查 `git diff` 确认实现分支未篡改既有的 `tests/acceptance/<slice>.rs` 断言且未残留未授权 `#[ignore]`；审查新增单测是否存在无有效断言的 `Reward Hacking` 投机测试，必要时运行 `cargo-mutants` 等 `Mutation Testing` 工具篡改源码运算符以验证测试集真实杀伤力。
2. 契约与 `SSOT` 语义对齐：对照所属 `context.md`、`context-map.md` 与已合入 `ADR`，核查新增类型、字段、路由与界面命名是否严格对齐统一语言 `等价` 标识符且未混入 `避免` 禁用词；检查对外契约演进是否遵循 `Parallel Change` 向后兼容规则（如通过 `oasdiff` 校验 `contracts/openapi.json`）以及读路径是否存在 N+1 查询退化。
3. 高杠杆并发与表面实测：针对涉及状态锁定、并发库存扣减或额度核销的写路径，校验是否具备覆盖随机时序不变量的 `Property-Based Testing`（如 `proptest-state-machine`）；针对图形客户端或命令行应用，对照 `Feature Map` 与界面属性验证要求在真实窗口或终端执行探索性走查并复核亮暗双主题 `Golden Snapshot` 差异。
4. 输出沙漏下口审查摘要：汇总检验范围、通过结论、状态机与契约影响面、并发与表面实测证据以及建议沉淀进护栏的改进条目，不得遗漏任何失败或降级跳过的检验步骤。
