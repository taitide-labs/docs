在基于最新主干分支拉出的隔离 `Worktree` 内完成交付，严格遵守冻结只读区边界与静态检查门禁，仅通过工作区统一任务入口验证并将全部结果交由自动化测试证明。

## 前置纪律与模式分发

- 冻结防线：严禁篡改上游共享契约、数据库迁移脚本、共享 `domain` 签名及黑盒验收测试的既有断言以防 `Reward Hacking`（仅允许移除工单中显式授权取代的旧规则场景），应当仅在工单所属切片自治区内编写实现；当确认上游契约存在真实缺口时，必须立即中止当前切片分支并回到主干通过 `design` Skill 走存量变更流程。
- 注释纪律：严禁编写普通代码注释，应当通过命名与受限类型表达意图；局部反直觉行为或绕过应当通过命名精准的回归测试锁定，仅允许编译器或工具链消费的结构化注释（如 `///`、`// SAFETY:` 与带 `reason` 的编译豁免）。
- 当处理不涉及业务规则或契约变更的纯实现缺陷修复时，先补齐复现失败测试再修复根因并跑通统一门禁，无需进入 `design` 流程。
- 按工单类型每次仅读取下列唯一一份执行指南：
  1. 服务端命令或查询垂直切片：读取 [backend-slice.md](references/backend-slice.md)。
  2. 命令行垂直切片：读取 [cli-slice.md](references/cli-slice.md)。
  3. 末尾跨上下文端到端联调、契约导出或前后端切换工单：读取 [e2e-cutover.md](references/e2e-cutover.md)。

## 统一交付门禁

1. 当全新 `Worktree` 缺少未追踪依赖目录（如前端 `node_modules`）时，先补齐环境依赖；严禁直接调用底层零散检查命令，必须使用 `mise run fmt` 自动修复排版格式，随后执行 `mise run check` 确认全量文档、架构规则、编译门禁、隔离测试与依赖许可审计全部通过。
2. 严禁直接推送 `main`，必须遵循 Conventional Commits 规范提交仅包含本任务自治目录的变更，推送独立分支创建 PR 并关联关闭对应工单（如有），等待门禁通过后按仓库规则合并。
